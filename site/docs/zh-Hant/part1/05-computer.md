# 第 5 章 共享雲電腦：檔案、瀏覽器與接管

剛接觸 Grok Bot 的使用者通常會產生幾個常見誤解。這些誤區往往會導致後續開發和維護遇到障礙：

- 誤以為新建一個 Bot 就會多出一臺獨立的虛擬機器。
- 誤以為讓幾個 Bot 一起幹活時，它們能直接讀懂對方的聊天記錄。
- 在需要第三方工具登入時，直接把賬號密碼甚至 API Token 貼進聊天視窗。

等到雲電腦因為系統維護或底層更新突然清空，安裝好的環境和指令碼全沒了。此時大家才發現自己對這臺雲電腦的底層機制一無所知。

同一賬號下的所有 Bot 都在同一臺雲端計算機上工作，共享同一個磁碟與檔案系統。它們看不見彼此的會話記錄，協作全靠磁碟上的檔案流轉。

遇到登入驗證時，正確的做法是直接在雲端瀏覽器接管螢幕輸入憑據，而不是把密碼交給模型。同時這臺雲電腦本質上是一個隨時可能被重新構建的臨時容器，平臺底層更新或管理員執行維護時，手動安裝的軟體包都會丟失。

這一章帶你拆解這臺雲電腦的真實工作方式。你將學會怎樣在多 Bot 之間安全交接檔案與螢幕、如何透過本地桌面路由網路流量以應對白名單限制，以及如何用一套輕量標準化的備份流水線，讓整個環境在經歷重置後能夠有條不紊地快速恢復。

## 共享電腦的底層機制：一臺機器與多個 Bot

**你賬號下的所有 Bot 共用同一臺託管 Linux 電腦。** 無論切到哪個 Bot，面對的都是同一個 `/workspace` 根目錄和持久磁碟。

聊天記錄獨立儲存在外部，即使在機器裡執行 `rm -rf` 刪空或系統崩潰重啟，對話與列表依然都在。

**新建 Bot 不等於安全隔離。** 任何 Bot 只要拿到命令列許可權，就能讀寫 `/workspace` 裡的所有資料，千萬別在裡面放未經加密的敏感資訊。

版本演進：
- v0.68.0：支援在設定中移除其他電腦
- v0.68.1（2026-10-07 釋出）：螢幕解析度從 1280×800 升到 1920×1200，操作與截圖響應更快
- v0.70.2：增加專屬郵箱，支援網頁直接存為 PDF

底層細節可看 [《4.6 虛擬機器、記憶與備份》](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)。

## 多 Bot 螢幕與工作狀態監控

### 狀態與配置

**側邊欄常駐三類狀態**。
- 需關注：等回答、審批或交接。
- 未讀活動：已完成任務，等看結果。
- 工作狀態：正在跑指令碼、抓網頁或調工具。

點頂部名稱進「檢視對話詳情」，可改當前 Bot 的名稱、標籤與頭像。個人 Bot 沒單獨描述框，**直接發訊息**就能調定位。

### 監控與通知

雲端操作支援**實時看螢幕**。

**處於焦點時通知自動抑制**，只在側邊欄和 Dock 標未讀；離線可在配置檔案開通知，推送到桌面或手機。

## 瀏覽器接管：移交螢幕，不交密碼

![瀏覽器接管：移交螢幕，不交密碼](/info/05-computer-s3.png)

別把賬密發進聊天框。你和 Bot 共用瀏覽器，**移交螢幕，不交密碼**。

### 接管步驟

1. 觸發暫停：Bot 開啟登入頁，遇賬密、掃碼或 2FA 時暫停。
2. 接管輸入：點選全屏接管鍵鼠。
3. 人工登入：自填賬密或掃碼驗證。
4. 移交執行：**登入後通知 Bot 複用 Cookie 執行**，碰不到明文密碼。

### 審批閘門

按 `Cmd+,` 在「常規」-「Bot」設定。

- **規則衝突以「先詢問」（Ask first）為準**。
- 企業規則顯示 `Required by your admin. You can't edit or delete this rule.` 無法修改。
- v0.70.2 強化了發信與發帖、支付以及改生產環境前的確認。

詳見 [設定和通知](https://cursor.com/cn/docs/grok-bot/settings)。

## 多 Bot 檔案交接約定與目錄規劃

### 檔案協作模式

Bot 間讀不了聊天記錄，**多 Bot 協作的唯一通道是共享磁碟檔案**。

提示詞只需傳入上一棒檔案路徑，詳見 [《4.6 虛擬機器、記憶與備份》](https://jcng5q8n0f3z.feishu.cn/wiki/KUggwkhqqiRyxZkwTLhcrCU2ncg)。

1. 整理員抓取生成 `tweets.md`
2. 分析師提煉輸出 `profile.md`
3. 設計師依畫像生成 `design.md`
4. 工程師讀設計構建程式碼

### 目錄規劃

建機之初定好目錄，免得多 Bot 把檔案寫亂。

| 目錄路徑 | 存放內容 | 寫入規範 |
| --- | --- | --- |
| `/workspace/handoff/` | 中間產物 | 統一 Markdown 或 JSON，帶任務字首 |
| `/workspace/projects/` | 專案程式碼與資產 | 按專案分獨立子目錄，關聯 Git 倉庫 |
| `/workspace/tools/` | 本地自寫指令碼 | 僅留無金鑰原始碼，排查後同步備份倉 |
| `~/.env` 或本地檔案 | API 金鑰 | 僅儲存在本地，**嚴禁提交程式碼倉或在會話列印** |

### 磁碟清理與 Disk Saver

系統報 `Computer is low on disk space` 或 `Computer is critically low on disk space` 警告，去側邊欄點 **Disk Saver** 的「Go to Disk Saver」看清理建議。

**未經確認它絕不擅自刪除檔案**，拒絕清理現有檔案就原樣保留。

## 本地網路出口：路由與訪問私有網路

![本地網路出口：路由與訪問私有網路](/info/05-computer-s5.png)

解決微信公眾號、企業內網 IP 白名單或區域網訪問，**走本地裝置中繼流量就行**。

### 開啟步驟
1. 按 `Cmd+,` 進設定，點 **計算機**。
2. 在 **你的計算機** 找到當前電腦，開啟 **透過當前計算機路由流量**。

### 限制與避坑
- 每次限單臺。外部識別為本地 IP，Bot 也能直接訪問區域網。
- **僅對新請求生效**，已有 TCP 長連線仍走原路線。
- 管理員若關 `Allow Local Egress Routing`，開關置灰提示 `Disabled by your admin. You can't turn this on.`，5 分鐘內強制斷開，見 [設定和通知](https://cursor.com/cn/docs/grok-bot/settings)。
- `Execution on this computer` 控制本地 Shell，預設逐條確認，**切勿隨意放開全自動**。

## 重建、更新與終止：雲電腦的生命週期

![重建、更新與終止：雲電腦的生命週期](/info/05-computer-s6.png)

重構**清空自裝環境**，保留磁碟與登入態。

見 [Grok Bot 計算機](https://cursor.com/cn/help/grok-bot/computer-recovery) 和 [管理 Grok Bot 電腦](https://cursor.com/cn/docs/grok-bot/computers)。

| 操作 | 保留 | 清除與坑點 |
| - | - | - |
| 軟體更新 | 全部 | 無 |
| 更新/重建 | 磁碟與檔案 | 清自裝環境；重跑指令碼 |
| 終止 VMs | 磁碟 | 閒置 30 天關機丟進度 |
| Recover/Reset | 已存資料 | 中斷任務，丟未存程式碼 |

顯示 `Reconnecting` 時**別盲目 Reset**，按順序排查。

1. **點 Retry**。重連中磁碟完好，亂點破壞現場。
2. **徹底退出**。macOS 需 `Cmd+Q` 退出再重啟，別隻點紅叉。
3. **查更新**。進「設定」>「計算機」，Bot 空閒再更新。
4. **優先 Recover**。彈出選項先選它，儘量存快照。
5. **最後 Reset**。確認無未存程式碼且全失效再重置。

## 災備流水線：服務總賬與冪等恢復指令碼

![災備流水線：服務總賬與冪等恢復指令碼](/info/05-computer-s7.png)

更新或重置會清空環境。铁柱AGI（@cgnot996）在 2026-10-10 提出方案，**只備拉起方法，不存整機**。

他用 5.1MB 私有倉庫管 10 個 Bot 的 20 個服務（18 項必恢復，含 4 個常駐、14 個按需與 2 個金鑰路徑項），詳見[教程](https://jcng5q8n0f3z.feishu.cn/wiki/Q6ZdwzjO5i6z0pkdMfyca8Cbnye)。

### 規範結構與入賬

倉庫 `vm-services` 包含四部分。
- `REGISTRY.md` 與 `registry.json`：總賬及配置。
- `restore/restore-<服务名>.sh`：單服務指令碼，**必須冪等**。
- `restore/restore-all.sh`：依序裝庫、CLI 並起後臺服務，統計失敗。
- `service-src/`：原始碼歸檔，排除 `.env`、日誌與虛擬環境。

新服務登記包含這幾項。短 ID 與負責 Bot；程式碼及資料路徑；安裝方式（apt/pip/npm/Docker）與系統依賴；啟動和檢查命令（--version 或埠）；是否必恢復；金鑰絕對路徑（**嚴禁記錄明文**）；掃碼或 OAuth 等步驟。

### 兩套提示詞

發給「虛擬機器服務管家」Bot，其他 Bot 部署依此交差。

::: details 部署與登記提示詞
```text
你是「虚拟机服务管家」，只管一件事：记下这台虚拟机上部署过的所有第三方服务，并在电脑更新或换账号之后，按记录把它们原样恢复。

你维护的东西：
1. 一份登记总账，人和机器各读一份：REGISTRY.md（表格）和 registry.json（给脚本读）。
2. 每个服务一个恢复脚本 restore/restore-<服务>.sh，必须幂等，重复跑也不会出错。
3. 一个总入口 restore/restore-all.sh，按依赖顺序调用各个恢复脚本，最后汇总哪些失败了。
4. 一份源码备份 service-src/：各 Bot 自己写的服务代码和脚本，同步时排除密钥、日志、运行状态、虚拟环境和个人数据，并先扫一遍明文密钥，命中就停。
5. 以上全部跟着一个私有 Git 仓库存（「你的备份仓库地址」）。总账、恢复脚本、源码都在仓库里，密钥永远不进仓库。

登记规则（其他 Bot 部署任何服务都必须来找你登记）：
每项必须包含：
- 名称和短 id、用途、负责的 Bot
- 路径：代码、配置、数据分别在哪
- 安装方式和依赖（apt / pip / npm / Docker / 系统定时任务）
- 启停命令、健康检查命令
- 更新后的恢复步骤，或者对应的恢复脚本
- 是否必恢复：是 / 否
- 密钥：只写存放路径，绝不写明文
- 需要真人完成的步骤（OAuth 登录、扫码、导入 cookie）单独标出来

你的工作方式：
- 先弄清哪些会丢、哪些能留：电脑更新一般保留工作目录，但系统包、常驻进程、全局安装的命令行工具会丢；重置则什么都不留。所以要记的是“怎么重建”，不是去拷整台机器。
- 能从公开渠道重装的（apt、pip、npm、上游 Git 仓库）只记安装命令；自己写的代码必须进源码备份，否则重置后就找不回来。
- 收到登记先核对：路径是否真实存在、健康检查能不能过。登记写的和实际不一样时，以实际为准，并告诉负责的 Bot。
- 多个定时任务合并成一份 crontab 真源时，检查每一条是不是都在真源里，不在的要靠恢复脚本补回去。
- 故意停掉的服务要写清楚“为什么停、什么条件下重开”，免得被当成漏装。
- 只有主人说“电脑更新完了”才跑总恢复，不盲跑。跑完交验收：每项是成功、失败，还是要真人处理。
- 每次有服务新增、删除或源码大改，先重新同步源码备份，再把总账、脚本、源码一起提交推送到备份仓库。换账号或重置时，就靠这份备份把整套设定带走。
- 删掉的服务要彻底清除：总账只反映现在真实的状态。
```
:::

重置後配好 Git 憑證發給恢復 Bot。**驗收標準按清單彙報結果、用時與檢查狀態**。

::: details 重置後的一鍵恢復提示詞
```text
这台电脑刚重置过（或者是换了新账号），之前部署的服务都没了。请按我的备份把它们恢复到可用状态，规则如下。

备份在哪：
- 备份仓库：<你的备份仓库地址>，分支 <分支名>
- 仓库里有：登记总账（REGISTRY.md 和 registry.json）、每个服务的恢复脚本（restore/）、自写服务的源码备份（service-src/）
- 仓库里没有密钥，这是故意的

请按这个顺序做：
1. 把备份仓库拉到工作目录，先读总账，告诉我一共登记了几项、哪些标了「必恢复」、哪些只留密钥不用恢复。先列出来，不要动手。
2. 把自写服务的源码从 service-src/ 放回总账写的原位置。只补缺失的，已经存在的目录不要覆盖。
3. 按总账的依赖顺序逐项恢复：先装系统依赖（比如 cron、ffmpeg），再装命令行工具，最后拉起常驻服务和定时任务。每项都用它自己的恢复脚本，脚本要能重复跑。
4. 每装完一项就跑它登记的健康检查。失败了先看日志、试着修一次；修不好就记下原因，接着做下一项，不要卡住。
5. 把需要我本人做的事汇总成一张清单：要重新提供的密钥（只说放哪个路径、叫什么名字，别让我把密钥贴进聊天）、要重新登录授权的工具（OAuth、扫码、设备码）。然后一项一项带我做，每做完一项马上复查。
6. 故意暂停的任务保持暂停，总账里写了原因和重开条件的照办。别因为“看起来漏装了”就自作主张打开。
7. 最后交验收清单，每项一行：服务名、结果（成功 / 失败 / 等我处理）、健康检查输出摘要、花了多久。再告诉我总共用了多少时间、成功了几项。

不要做的事：
- 不要把任何密钥写进仓库、日志或聊天
- 不要跑总账没登记的安装
- 不要用“重置电脑”当修复手段
- 恢复完如果有任何改动（路径变了、版本升级了），更新总账，提交推回备份仓库
```
:::

## 容易踩的坑

### 憑證與許可權
- **別在聊天框貼金鑰**：網頁端手動輸；CLI 的 Token 寫入 `~/.env`，指令碼讀環境變數。
- **Bot 間無隔離**：共享 `/workspace` 與許可權。敏感資產靠私有倉庫和人工審批，多開沒用。

### 協作與依賴
- **交接須落盤**：Bot 互不讀會話。A 的結果存為 Markdown 或 JSON，光靠說 B 會幻覺。
- **依賴不持久**：更新、Recover 或 Reset 會清空 `apt install` 與 `npm install -g` 的內容，`node_modules` 和 `.venv` 也不備份。

  **恢復指令碼須包含** `npm install` 與 `pip install -r requirements.txt`。

### 運維與網路
- **見 Reconnecting 別按 Reset**：會丟未存檔改動並強行重建，**先重試或重啟客戶端**。
- **定時任務集中管**：crontab 須統一存入 Git 倉庫維護。
- **開本地路由須重啟**：開啟「透過當前計算機路由流量」若 IP 沒變，重啟該程序。

## 做完怎麼驗收

1. Bot A 往 `/workspace/handoff/test.json` 寫時間戳。**Bot B 讀取並準確說出**即通暢。
2. 在「設定」>「計算機」開啟「透過當前計算機路由流量」，終端跑 `curl -s https://api.ipify.org`。**外網 IP 需與本地一致**，非機房 IP。
3. 讓 Bot 開啟 GitHub 登入頁，**必須在密碼框前暫停並提示移交**。手動登入後繼續，確認日誌無明文密碼。
4. 確認私有 Git 已提交 `REGISTRY.md`、`registry.json` 與指令碼。在測試目錄拉取並執行：
```bash
bash restore/restore-all.sh
```
**健康檢查需全數透過**，無衝突報錯，總賬服務正常監聽。
