# 제10장 크레딧과 비용: 1주일 사용량으로 일주일 꽉 채워 쓰기

화요일에 크레딧이 바닥나고 수백 달러가 청구되는 일은 대개 컴퓨팅 파워의 공회전 때문입니다. **Bot은 깨어날 때마다 전체 대화 기록을 다시 읽으므로**, 불과 몇 시간 만에 수십만 토큰으로 부풀어 오릅니다.

일주일을 안정적으로 버티려면 다음 세 가지를 잘 챙겨야 합니다.
1. 백그라운드 온디맨드(종량제) 결제를 끕니다.
2. 고주기 폴링과 여러 Bot 간의 상호 대화를 줄입니다.
3. 세션을 타이트하게 관리하고, 채팅창에 대용량 파일을 넣지 않습니다.

## Grok Bot의 크레딧 차감 원리는 무엇인가요? {#扣费原理-额度是怎么被花掉的}

**Grok Bot은 호출된 토큰 기준으로 과금되며, 핵심 메커니즘은 단일 롱 세션 대화 방식입니다. 매번 답변하거나 깨어날 때마다 이전 컨텍스트 전체를 다시 읽으므로, 총 소모량은 깨어난 횟수에 매번 다시 읽는 컨텍스트 길이를 곱한 값과 같습니다.**

![과금 원리: 크레딧은 어떻게 소모되는가](/info/10-usage-s1.png)

Grok Bot은 모델이 실제로 호출한 토큰 수에 따라 과금됩니다. **핵심 메커니즘은 단일 롱 세션 대화로, 매번 응답하거나 정기적으로 깨어날 때마다 전체 대화 기록을 처음부터 끝까지 다시 읽습니다.**

```
每周总消耗 = Bot 唤醒的总次数 × 每次唤醒时重读的上下文长度
```

세션에 대량의 로그나 웹페이지가 쌓이면 1회 재독기록만으로도 수십만 토큰에 달할 수 있으며, 단 한 문장을 답하더라도 전체 분량이 계산됩니다.

커뮤니티 분석은 [《How to Stop Your Grok Bot From Eating a Week of Usage in a Day｜Fan Grok Bot Radar》](https://jcng5q8n0f3z.feishu.cn/wiki/HO20w5OQQiNtNuk92mhcdQEynOi)를 참고하세요.

크레딧 규칙에 대한 자세한 내용은 [Cursor 공식 가이드: 플랜 및 결제](https://cursor.com/cn/help/grok-bot/plans)를 참조하세요. 일상적인 사용 시 몇 가지 엄격한 제한 사항이 있습니다.

- **크레딧 풀 중복 불가**: 여러 요금제를 구독하더라도 주간 크레딧이 가장 높은 한 가지만 적용되며, 합산되어 누적되지 않습니다.
- **공유 풀 범위**: 주간 크레딧은 Grok Bot 및 Cursor 내의 Grok뿐만 아니라 웹, 모바일, Imagine, Voice까지 포함하며, 만료 시 고정 주기로 초기화됩니다.
- **타사 모델 별도 과금**: Cursor 내에서 Grok 외의 모델을 호출할 경우 종량제로 직접 과금됩니다.
- **온디맨드 결제와 월간 한도**: 주간 크레딧이 소진된 후 On-demand를 활성화하면 월간 한도(Monthly Limit)에 반영되며, 한도를 초과하더라도 진행 중인 작업은 끝까지 실행됩니다. 비활성화하면 응답을 중단하고 초기화를 기다립니다.

**공식적으로 모델 선택기(there is no model picker)가 없다고 명시되어 있어 저사양 모델로 전환할 수 없습니다.** 비용을 통제하려면 깨어나는 빈도를 줄이거나, 컨텍스트 길이를 잘라내거나, 리소스 소모가 큰 연산을 외부로 분산시키는 방법밖에 없습니다.

## Grok Bot의 흔한 고소모 크레딧 함정에는 어떤 것들이 있나요? {#高耗操作清单-坚决避开的六大陷阱}

**여러 Bot 간의 그룹 채팅, 대화창에 이미지 및 영상 직접 입력, 24시간 고주기 폴링, 하나의 긴 세션을 끝까지 사용하기, 보호 조치 없는 재시도 무한 루프, 그리고 월간 한도를 설정하지 않은 채 무분별하게 온디맨드 결제를 켜는 일은 반드시 피해야 합니다.**

| 여러 Bot의 그룹 채팅 | 상호 호출로 인해 토큰이 배로 헛돌게 됨 | 단일 주도 Bot에 Subagents를 배치해 업무 분담, 또는 사람이 1:1 대화 |

| 24시간 고주기 폴링 | 15분마다 1회 시 주 672회 실행되며, 대부분 변경 사항 없음을 확인하는 데 소모 | 업무 시간으로 축소하거나 시스템 스크립트 + Webhook으로 전환 |
| 단일 세션을 끝까지 사용 | 수십 턴 후 단일 턴 재독만으로 수십만 토큰 소모 | 1작업 1세션 원칙 준수, 정기적으로 요약 후 Duplicate로 초기화 |
| 보호 조치 없는 재시도 무한 루프 | 오류 발생 후 스스로 수십 차례 연속 재시도 | **프롬프트에 재시도 상한을 2회로 강제 설정**, 실패 시 즉시 중단하고 사람에게 질문 |
| 무분별한 종량제 결제 활성화 | 무한 루프로 인해 하룻밤 사이에 거액의 청구서 발생 가능 | **평소에는 온디맨드 결제를 끄고**, 활성화 시 반드시 엄격하게 낮은 월간 한도 설정 |

## 크레딧 절약 4단계 워크플로: 손실 방지부터 부하 분산까지

![크레딧 절약 4단계 워크플로: 손실 방지부터 부하 분산까지](/info/10-usage-s3.png)

### 결제 및 보안 마지노선 고정
1. Settings > Usage & Billing으로 이동하여 요금제(Premium 월 $30 또는 Super 월 $100), 사용량, 카운트다운을 확인합니다. 작업이 멈추면 Stop을 눌러 강제 종료합니다.
2. **디버깅 시에는 Additional Usage / On-demand를 끕니다.** 켜야 할 경우 cursor.com/dashboard > 지출 > Monthly Limit에서 월 한도($10~$20)를 설정합니다.
3. Settings > General > Auto-review로 이동하여 **send, post, buy, transfer, delete, permissions를 Ask first(수동 승인)로 설정합니다**.

### 세션 및 인터랙션 표준화
- **1작업 1세션**, 작업이 끝나면 즉시 보관합니다.
- 긴 로그 텍스트는 `/workspace/`에 저장하고 결론과 경로만 회신하며, 대화창에 직접 붙여넣는 것을 엄격히 금지합니다.
- X 검색은 분당 30회, 일일 1,000회로 제한되며(주간 크레딧 차감 없음), **Bot에게 "핵심 사실만 추출하여 3~5개 요점으로 출력하라"고 제한합니다**.
- 세션이 비대해지면 Duplicate로 초기화합니다. 먼저 이전 Bot에게 10줄 이내로 요약하도록 한 뒤, 이를 복사해 새 Bot에게 전달하여 인계받게 하고 이전 Bot은 숨깁니다.

### 기능 라우팅 및 부하 분산
- 메인 Bot은 분해, 할당, 취합만 담당하며 긴 코드를 작성하거나 대용량 파일을 변환하지 않습니다.
- **코드 작성은 Cursor 클라우드 Agent를 이용하거나**(Cursor 크레딧을 사용하며 주간 크레딧은 차감되지 않음), 가상 머신에서 헤드리스로 Grok Build CLI / Codex CLI를 실행합니다.
- 스크린샷과 오디오/비디오는 클라우드 PC 명령어로 처리하거나, 무료 모델을 사용해 텍스트로 변환한 후 Bot에게 전달합니다.

### 예약 작업(루틴) 개편
1. Details > Routines에서 **지난 일주일 동안 매일 "변경 사항 없음"만 보고하던 루틴을 일시 중지하거나 삭제합니다**.
2. 저비용으로 폴링하는 Linux 스크립트로 교체하고, 변경 사항이 있을 때만 Webhook을 보내 Bot을 깨웁니다.
3. **유지할 루틴에는 무언 지침을 작성합니다**: "확인 후 변경 사항이 없으면 즉시 작업을 종료하고 어떤 텍스트도 출력하지 말 것".

## 루틴 및 폴링 심층 최적화: 무의미한 공회전 없애기

루틴은 숨겨진 크레딧 블랙홀이며, 고주기 폴링은 **단 하루 만에 일주일 치 사용량을 전부 소모할 수 있습니다**.

### 실행 주기 축소 및 실행 윈도우 제어

클라이언트에서 먼저 Bot의 Timezone이 로컬 시간대와 일치하는지 확인합니다. 스케줄 설정에 따른 소모량은 다음과 같습니다:

| 스케줄 설정 | 주간 실행 횟수 | 적용 시나리오 |
| :--- | :--- | :--- |
| 15분마다 1회 (24시간) | 672회 | 1~2일 만에 크레딧을 소진하기 쉬우며, 필요한 경우가 극히 드묾 |
| 매시간 1회 (24시간) | 168회 | 핵심 인프라 장애 모니터링 |
| 평일 09:00~17:00 매시간 1회 | 45회 | 칸반 트래킹, 티켓 처리 및 이메일 분류 |
| 평일 매일 3회 | 15회 | 일일 수신함 아침·점심·저녁 1차 선별, 진행 상황 추적 |
| 주 1회 | 1회 | 업계 주간 리포트, 기술 동향 요약 및 문서 보관 |

업무 시간으로 한정하려면 표준 cron 형식을 사용할 수 있습니다:

```text
CRON_TZ=Asia/Shanghai 0 9-17 * * 1-5
```

**이 규칙 한 줄로 호출 횟수를 93% 줄일 수 있습니다.** 상하이 시간대 기준 평일 09:00부터 17:00까지 정각마다 실행되어 일주일에 단 45회만 트리거됩니다.

### 스킬을 지정하고 침묵 규칙을 엄격히 준수하기

루틴 프롬프트는 스킬만 지정하고 세부 사항을 길게 풀지 않습니다:
- 슬래시 명령어로 구체적인 스킬 이름과 검사 대상 지정
- 판정 임계값, 중단 조건, 단일 재시도 제한 제공
- **변경 사항이 없을 때는 완전히 침묵을 유지하며 어떤 메시지도 보내지 않기**

완전한 침묵은 도중의 장애를 가릴 수 있습니다. 권장 조합 방안은 [Cursor 공식 가이드: 루틴](https://cursor.com/cn/help/grok-bot/routines)을 참고하세요. 고주기 루틴은 침묵을 유지하고, 저주기 루틴은 매일 18:00에 한 줄짜리 하트비트 로그를 보내 지난 하루 동안 정상 실행되었음을 확인합니다.

### 이중 역할 분리: Linux cron 스크립트 점검 + Webhook 호출

Bot이 절전 상태일 때도 기본 Linux 클라우드 PC는 계속 실행 중이므로, **거대 모델에게 기계적인 단순 비교 작업을 시키지 마세요**.
- 검사 역할: 시스템 내장 cron이 Python 또는 Shell 스크립트를 스케줄링하여 비교합니다. 몇 초밖에 걸리지 않으며 크레딧 소모는 0입니다.
- 판단 역할: 스크립트가 변경 사항을 감지했을 때만 Webhook을 보내 Bot을 깨워 논리적 판단과 보고를 수행하게 합니다.

Webhook 호출 단계 및 검수 기준:
1. 루틴 Webhook 영역에서 `POST to` 주소와 `key`를 가져옵니다.
2. 해당 URL로 `Authorization: Bearer <key>` 헤더를 포함한 POST 요청을 보냅니다.
3. 응답 상태 코드를 확인하여 200이 반환되면 성공적으로 호출된 것입니다.

## 그룹 채팅 및 다중 Bot 제어: 상호 호출 원천 차단

**여러 Bot을 절대 같은 그룹 채팅에 초대하지 마세요.** 새 메시지가 모든 멤버에게 브로드캐스트되어, 각 Bot이 전체 대화 기록을 다시 읽고 응답하게 됩니다. 铁柱의 경험담에 따르면 4개의 Bot이 서로 대화하다가 순식간에 주간 할당량의 25%를 소진했다고 합니다(미검증).

다중 Bot 협업은 **허브 앤 스포크 방식을 고수하고 횡적 연결을 금지**해야 합니다.

- 유일한 주도권: 상호작용 입구로서 단 하나의 주도 Bot만 유지합니다.
- 단방향 업무 전달: 주도 Bot이 Subagents를 시작하거나 A2A 단일 지점 인계를 수행하며, 서브 에이전트는 작업이 끝나면 자동으로 종료되고 그룹 대화에 끼어들지 않습니다.
- 결과물 디스크 저장: 상위 작업자가 `/workspace/` 아래의 파일에 데이터를 기록하면 하위 작업자가 이를 직접 읽으며, 채팅창에서 장황하게 논의하지 않습니다.
- 유휴 상태 정리: 연결된 루틴이 없음을 확인한 후 유휴 Bot을 제때 삭제하여 잘못 깨어나는 것을 방지합니다.

## Grok Bot의 사용량 감사 및 소진 시 비상 대처는 어떻게 하나요? {#用量审计与应急机制-守住每周节奏}

**매주 리셋 전날 15분을 투자해 루틴 기록과 차감 내역을 확인하세요. 크레딧이 소진되어 프론트엔드가 잠기더라도 기본 Linux 클라우드 PC는 삭제되지 않으므로, 터미널을 직접 열어 코드를 인계받고 수동으로 커밋 및 푸시할 수 있습니다.**

### 주간 15분 감사 절차

매주 초기화되기 전날 15분을 들여 다음 사항을 확인할 것을 권장합니다:
1. Settings > Usage & Billing을 열어 사용된 비율(%)을 확인합니다. 소모가 지나치게 빠르다면 이전 며칠간의 작업을 불러와 이상이 발생한 날짜를 파악합니다.
2. Details > Routines로 이동하여 최근 20회의 실행 기록(Running, Succeeded, Failed)을 확인하고, 오류 재시도나 빈번한 공회전이 발생한 루틴을 찾아냅니다.
3. v0.66.0부터 지원되는 별표 메인 Bot의 경우, 스스로 잡무를 떠맡지 않도록 **설명에 먼저 나서서 작업을 맡는 것을 금지한다고 명시**합니다.
4. cursor.com/dashboard에 접속하여 Monthly Limit과 실제 온디맨드 결제 금액을 대조하고, 비정상적인 결제가 없는지 확인합니다.

### 모니터링 사각지대와 대응법

시스템은 개별 Bot, 루틴, 세션, 모델별 소모 상세 내역을 제공하지 않으며, 20개의 실행 기록에도 토큰 수와 금액이 기록되지 않습니다. **새로운 프로세스를 테스트할 때는 반드시 변인 통제법을 적용해야 합니다**:
1. 한 번에 하나의 Bot 또는 루틴만 새로 만들거나 수정합니다.
2. 실행 전후에 Usage & Billing의 백분율을 각각 확인하여 증가분을 비교하며, 절대 여러 개의 새 루틴을 동시에 배포하지 마세요.

### 크레딧 소진 시 클라우드 PC 직접 인계 응급 대처

주간 크레딧이 100% 소진되어 프론트엔드 대화가 잠기더라도 기본 Linux 클라우드 PC는 삭제되지 않습니다. 클라이언트를 통해 데스크톱이나 시스템 터미널을 열어 다음과 같이 직접 인계받을 수 있습니다:
1. `/workspace/` 디렉터리에서 아직 전달되지 않은 코드와 파일을 확인합니다.
2. 수동으로 `git commit` 및 `git push`를 실행하여 원격 저장소로 푸시합니다.
3. 로컬 명령줄 도구를 사용하여 터미널에서 디버깅을 이어가며, **추가 사용량을 구매하기 위해 돈을 쓸 필요가 전혀 없습니다**.

## Bot에게 직접 보내는 크레딧 절약 프롬프트 모음

### 컨텍스트 비대화 방지
- 규칙을 Bot에게 요약하여 기억하게 함으로써 **대화 때마다 반복해서 설명하는 수고를 덜 수 있습니다**. 공유 Bot의 경우 상세 정보의 About에 작성할 수 있습니다.
```text
请回顾我们至今的协作流程，执行两项沉淀工作：
1. 把你需要长期遵守的行为边界、汇报格式与约束规矩，提炼成一段不超过 300 字的精简文本，我将直接粘贴到你的描述（Description）中；
2. 把我们刚才已经跑通的标准操作流程，封装为一个可复用的技能（Skill），供后续例程直接调用。
完成提取后直接在对话中给出文本，不要展开多余闲聊。
```
- 원시 로그와 긴 자료는 디스크에 강제로 저장하고, 세션에 직접 붙여넣지 않습니다.
```text
从现在起执行上下文瘦身规则：
所有抓取的长篇网页、接口调试日志、大批原始数据和阶段性中间产物，一律直接保存为 /workspace/ 目录下的文本文件。在聊天窗口中回复我时，严格只提供核心结论、关键变动要点以及对应的文件绝对路径。严禁将大段原始文本或日志代码贴回对话。
```
- 멀티모달 이미지는 명령줄 파싱으로 전환하여 **채팅창에서의 높은 소모를 회피합니다**.
```text
遇到查看多张截图、分析视频画面、逐帧拉片、音频转写或处理长扫描件的任务时，严禁在当前对话框中直接读取原始多模态文件。
你应当在云电脑终端中调用系统已配置的命令行工具（如 Grok Build 或相关转录 CLI）在后台执行，并输出简明的结构化文字摘要；你只需阅读生成的文字结论。如果当前环境无法执行命令行解析，请停下提醒我先在网页端转换成文字后再发给你。
```

### 작업 및 코드 부하 분산
- 모니터링 루틴에서 변경 사항이 없을 때는 조용히 종료합니다.
```text
请列出当前你名下的全部例行任务（Routines），注明每条任务的触发频率、每周预计运行次数以及没有变化时的处理逻辑。
找出其中运行最频繁、消耗最大的任务，向我提出降低频率的具体建议；同时为所有监控类例程添加硬性约束：执行检查后若目标无实质变动，立刻静默退出，严禁向我发送「一切正常」或「没有新消息」等无有效信息的通报。
```
- 작업은 1:1 대화로 전달하며, **Bot이 임의로 그룹을 만들어 대화하는 것을 엄격히 금지합니다**.
```text
严格执行独立单聊工作模式：
只接收并执行我本人下达的直接指令。严禁在没有得到我明确授权的情况下，主动在会话中唤醒、提及或联络其他 Bot 开展群聊协同；如果任务涉及多个专业环节，请将结果写成文件并由我来负责跨 Bot 调度，或者将其派发给云电脑内的后台 CLI 工具独立运行。
```
- Bot은 스케줄링에 집중하고, 긴 코드 작성과 디버깅은 **Grok Build 백그라운드 CLI로 분산시킵니다**.
```text
明确你的角色定位是任务调度主管，核心职责是理解目标、拆解方案、组织逻辑和验收结果。
不要在聊天窗口中直接编写整段的长篇代码，也不要通读整个大型仓库做全量重构。涉及代码编写、项目调试和环境排查的工作，统一在后台调用云电脑内已经授权的 Grok Build 命令行工具执行。执行完毕后，你仅需检查其退出状态码并将最终结论同步给我。
```

### 검색, 위험 관리 및 인수인계
- X 플랫폼 검색 결과는 디스크에 저장하고, 대화창에는 핵심 요점만 간결하게 보고합니다.
```text
在检索 X 平台的推文、观点或动态时，使用你自带的免费搜索能力。
搜索到的批量推文原文，请直接写入 /workspace/ 下的对应 markdown 文件中保存。在聊天框中向我汇报时，严格限制为 3 到 5 条提炼后的核心事实与推文对应链接，严禁把多条推文的大段原文搬运回聊天中。
```
- 자동화 및 API 호출에는 반드시 재시도 상한을 설정하고, **이상 발생 시 강제 중단 후 사람의 승인을 받도록 합니다**.
```text
在执行自动化任务、网络请求或文件排查时，严格执行防死循环规则：
同一操作或相似接口调用的重试上限为 2 次。如果连续 2 次重试均未成功，或者对下一步执行动作存在疑问，立刻中断自动化流程并向我发起提问，详细说明遇到的错误原因，严禁自行无限重试或在后台空转。
```
- Duplicate 복제 전 이전 Bot에게 인수인계 카드를 정리하게 하고, **엄격하게 10줄 이내로 제한합니다**.
::: details 搜索、风控与交接
```text
当前会话历史较长，需要进行交接重置。请为我梳理一份 10 行以内的结构化交接总结，严格包含以下五项内容：
1. 你的角色设定与核心职责；
2. 当前正在进行的任务目标；
3. 已经达成的关键结论与做过的核心决定；
4. 下一步必须立刻执行的动作；
5. 新会话需要优先读取的关键文件绝对路径。
输出完毕后不要执行任何新任务，等待我启动新会话。
```
:::
- 시크릿 입력창에 OpenRouter 무료 key를 입력하여 가벼운 작업을 바로 분산시킵니다.
```text
请协助配置 OpenRouter 免费模型调用环境，严格遵循以下安全执行流程：
1. 在聊天框中调出系统的密钥输入弹窗向我收取 API Key，严禁让我把密钥明文发送在普通对话中；
2. 将获取到的 Key 保存到 ~/.agents/secrets/openrouter.env 文件中，环境变量名指定为 OPENROUTER_API_KEY；
3. 对该密钥文件执行 chmod 600 设置安全权限；
4. 执行全程严禁在终端标准输出或聊天消息中打印该 Key 的明文内容；
5. 使用 curl 调用一个以 :free 结尾的免费模型进行一次最小文本测试，确认调用成功且费用为 0，并将测试结果告诉我。
```

## 빠지기 쉬운 함정

- Details > Routines에서 Test를 클릭하면 실제 환경 프로세스가 실행되어 **매번 실제 크레딧이 차감됩니다**.
- Cursor와 SuperGrok의 **크레딧은 합산되지 않으며**, 주간 사용량이 높은 쪽 하나만 적용되고 다른 한쪽은 유휴 상태가 됩니다.
- grok.com과 Grok Bot은 과금이 독립적이어서, 웹 버전에서 충전한 금액은 **차감에 사용할 수 없으며 환불도 불가합니다**.
- 채팅창에 API Key나 Webhook을 붙여넣는 것은 토큰을 낭비할 뿐만 아니라 위험하므로, **반드시 보안 팝업을 통해 환경 변수로 작성해야 합니다**.
- '컴퓨터 업데이트'를 클릭하면 Linux cron이 삭제되지만 `/workspace/`는 보존되므로, **업데이트 후에는 cron을 다시 설정해야 합니다**.
- Duplicate는 대화, learned memory 및 첨부 파일을 삭제하므로, **새 Bot에게 컨텍스트를 수동으로 제공해야 합니다**.
- Monthly Limit이 트리거되어도 프로세스가 강제 종료되지 않아 **장기 실행 작업은 끝까지 실행되므로**, 무한 루프가 발생하면 한도를 초과할 수 있습니다.

## 완료 후 검수 방법

1. Settings > Usage & Billing 및 cursor.com/dashboard에서 청구 내역을 확인하여 사용 비율(%)과 초기화 카운트다운을 확인하고, **Additional Usage를 끄거나 Monthly Limit을 안전하고 낮은 금액으로 설정합니다**.
2. Bot에게 파일 삭제 또는 외부 네트워크 요청을 시뮬레이션하도록 지시했을 때, 반드시 **Ask first** 승인 카드가 팝업되어 대기 상태로 유지되어야 하며 조용히 실행되어서는 안 됩니다.
3. 현재 세션을 점검하고 다수의 트윗을 검색하는 X 검색을 요청했을 때, 사이드바에 수십 턴의 긴 세션이 남지 않고 3~5개의 요약 보고만 반환되며, 긴 텍스트는 `/workspace/`에 저장되어 대화창에 원문이 도배되지 않는지 확인합니다.
4. Details > Routines로 이동하여 변경 사항이 없는 모니터링 루틴의 Test를 클릭했을 때, 확인 후 불필요한 "업데이트 없음" 같은 사족 없이 즉시 조용히 종료되는지 확인합니다.
5. Bot에게 여러 파일에 걸친 의존성 코드를 작성하게 했을 때, 백그라운드에서 Grok Build 또는 클라우드 Agent를 호출하여 **최종 상태와 실행 요약만 출력**하고, 채팅창에 화면 가득 코드를 붙여넣지 않는지 확인합니다.
