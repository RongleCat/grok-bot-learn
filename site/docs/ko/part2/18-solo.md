# 제18장 케이스 스터디: 1인 기업과 AI 팀

**동일한 계정의 모든 Bot은 단일 클라우드 컴퓨터를 공유**하며, 브라우저, 파일 시스템, 터미널이 기본으로 제공됩니다.

한 번에 십여 개의 Bot을 생성하고 모든 계정 권한을 넘기면 함정에 빠지기 쉽습니다.
- 외부 웹페이지에서 경로를 이탈하거나 데이터를 조용히 덮어씀
- 한밤중에 잦은 승인 요청을 트리거하여 검토 피로 누적

역할 경계, 자격 증명 격리, 승인 마지노선을 명확히 정리하면, **첫 번째 AI 직원을 구성하는 것부터 시작해 29개의 Agent를 관리하는 수준까지 발전**할 수 있습니다.

## 첫 번째 AI 직원: 채용하듯 역할과 권한 정의하기

![첫 번째 AI 직원: 채용하듯 역할과 권한 정의하기](/info/18-solo-s1.png)

Bot을 단순한 도구로 볼 것인지 아니면 직원으로 볼 것인지는 일회성 프롬프트를 작성하고 있는지, 아니면 업무 역할을 확립하고 있는지에 달려 있습니다. 일회성 프롬프트를 작성하면 당장 눈앞의 작업 하나만 처리하며, 창을 닫으면 컨텍스트가 사라집니다. 반면 업무 역할은 고정된 프로필 문서로, 해당 Bot이 매일 업무를 처리할 때의 행동 마지노선과 사고방식을 결정합니다.

### 역할 정의 및 진입 테스트

**처음부터 되돌릴 수 없는 권한을 주지 마세요.** 지루하고 빈도가 높으며 쉽게 취소할 수 있는 잡무부터 시작해야 합니다.

Bot에게 실무를 맡기기 전에, 두 가지 진입 테스트를 먼저 실행해 오류를 미리 방지하세요.
1. **한 줄 직무 테스트**: 무엇을 납품할지 한 문장으로 명확히 설명합니다. 관련 없는 동사를 4~5개나 욱여넣는 것은 한 사람에게 세 사람 몫의 일을 시키는 것과 같아, 오류가 발생했을 때 근본 원인을 파악할 수 없습니다.
2. **텍스트 시뮬레이션(Trial in text)**: 2분도 채 걸리지 않으며, 진행할 단계, 방문 예정 URL, 의문이 드는 판단 사항을 먼저 보고하게 합니다.

역할 기술서는 다섯 가지 필드로 나누어 경계를 명확히 구분합니다.
- Owns: 납품할 고정 결과물.
- Inputs: 읽기가 허용된 채널.
- May: 자율적으로 처리할 수 있는 작업.
- Must ask before: 비용 지출이나 설정 변경 등 위험도가 높은 작업은 **반드시 사람의 승인을 대기**.
- Done when: 객관적으로 대조할 수 있는 검수 체크리스트.

```text
先不要执行任何实际操作。请逐步向我推演你的完整执行方案：
1. 列出你准备依次打开的工具、网址与调用的插件。
2. 列出你在过程中需要做出的业务判断。
3. 标出你目前信息不足、存在疑虑或拿不准的决策点。
推演完毕后等待我的指令，严禁自行操作。
```

::: details 역할 정의 및 진입 테스트
```text
岗位名称：收件箱管理员（Inbox Manager）
Owns：
每天上午梳理工作邮箱，归档垃圾邮件与订阅通讯，起草客户咨询的回复草稿，标出需要我决策的紧急邮件。
Inputs：
仅限于 Gmail 中收件箱的未读邮件与公司提供的常见问题回复模版。
May：
阅读邮件、按标签分类、打上处理标记、撰写回复草稿、归档无回复价值的宣传邮件。
Must ask before：
严禁直接点击发送任何邮件；严禁归档来自财务、法务或房东的邮件；如果邮件涉及转账、退款、重置密码或修改凭证，立即停下向我确认。
Done when：
工作日上午 9:00 前收件箱所有未读邮件分类完毕；生成的草稿不超过四句话，语气平实直接，不使用任何客套空话；所有待办事项单独列出截止日期。遇到不确定如何处理的邮件，保持未读并挂起询问，严禁自行猜测意图。
```
:::

역할 설정과 임시 프롬프트는 완전히 다릅니다.

| 차원 | 임시 프롬프트 | 역할 설정 |
|---|---|---|
| **목표 및 형태** | 단일 대화, 일회성 작업에 집중 | 장기적 설정, 비즈니스 결과물 납품 |
| **경계 및 권한** | 구두 지시는 권한을 넘어서기 쉽고, 오류 발생 시 재실행 | 되돌릴 수 있는 작업은 자율 처리, 되돌릴 수 없는 작업은 승인 대기, 엄격한 휴먼 게이트 설정 |

새로운 Bot이 막 정상 작동했다고 해서 **절대로 백그라운드 무인 실행으로 직행하지 마세요**. 먼저 distort의 '3회 실행 법칙'에 따라 테스트해야 합니다.

1. 1회차 (전 과정 관찰): 화면을 주시하며 단계별 작업을 지켜보고, 지시 오독, 컨텍스트 누락, 임의 추측이 발생하는 지점을 기록합니다.
2. 2회차 (규칙 수정): 동일한 난이도의 다른 작업을 부여하되 이전 실수를 먼저 일러주지 않습니다. 결과물을 대신 수정해주지 않고, 역할 규칙과 권한 변경 사항이 제대로 적용되는지 중점적으로 확인합니다.
3. 3회차 (자율 실전 테스트): 전 과정을 개입하지 않고 지켜보다가, 승인 요청 시점이나 재시도 상한에 도달했을 때만 개입하여 완성도, 개입 횟수, 소요 시간, 사용량을 검증합니다.

**3회 테스트를 통과하면 승진 단계로 진입**하며, 5단계 권한으로 나뉩니다.

| 등급 | 메커니즘 | 경계 |
| :--- | :--- | :--- |
| Level 0 | 관찰 전용 | 어떠한 데이터도 변경하지 않음 |
| Level 1 | 준비 전용 | 검색, 요약, 서식 정리 등 되돌릴 수 있는 작업 |
| Level 2 | 사람 승인 | 핵심 단계에서 작업을 일시 중단하고 확인 대기 |
| Level 3 | 독립 실행 | 예약 또는 트리거 실행, 주기적으로 증거 체인 보고서 산출 |
| Level 4 | 멀티 Bot 협업 | 작업 분배 및 품질 검수 노드 역할 수행 |

다음 등급으로 승진하려면 4가지 **필수 기준**을 충족해야 합니다.
- 연속 5회 무결점 실전 실행
- 모든 검증 단계 통과
- 미해결 부작용 없음
- 롤백 메커니즘 검증 완료 및 사용 가능

## 바닥에서 시작해 돌아가는 회사 만들기: 비서실장과 전담 팀 편성

혼자서 Grok Bot을 사용해 완전한 비즈니스 운영 체계를 구축할 때 가장 빠지기 쉬운 막다른 길은 단일 Bot에 너무 많은 역량을 몰아넣는 것입니다. 영업 리드 관리, 콘텐츠 작성, 정산, 코드 수정까지 도맡는 Bot은 컨텍스트 윈도우가 무관한 선호 설정으로 금세 가득 차게 되며, 비즈니스 맥락을 혼동하기 쉬울 뿐만 아니라 사용량 소모도 가속화됩니다.

### 비서실장 아키텍처 및 부서 분할

팀을 꾸릴 때는 비서실장 Bot부터 만드세요. 일상적으로는 **비서실장하고만 소통**하며, 비서실장이 작업을 세분화하고 전담 역할을 조율하며 납품 결과를 종합합니다.

::: details 비서실장 아키텍처 및 부서 분할
```text
你是一人公司的幕僚长（Chief of Staff），也是我日常沟通的唯一入口。
你的核心职责：
1. 接收我的业务目标，拆解为明确的工作阶段，派发给对应的专职 Bot（调研、内容、代码、运维）。
2. 在群聊中调度各岗位接力，跟踪各任务交付状态。
3. 检查专职 Bot 提交的产物是否符合完成标准，核对数据来源与执行录屏。
4. 每天晚上汇总团队进展，用不超过五行文字向我汇报核心结果、阻塞问题与需要我决策的审批项。
行为底线：
若无任何新进展或异常，保持静默；严禁越权代替专职 Bot 编写业务交付内容；严禁绕过人工审批直接执行外发、扣款或修改生产环境。
```
:::

- 리서치 Bot: 결론에는 반드시 날짜와 URL을 명시해야 하며, 의문점은 선제적으로 표시하고 억지로 지어내지 않습니다.
- 콘텐츠 Bot: 템플릿에 맞춰 서식을 정리하며, **외부에 직접 게시하는 것을 엄격히 금지**합니다.
- 영업 Bot: 아웃리치 이메일은 모두 임시보관함에 저장하고, 사람의 승인을 받은 후 발송합니다.
- 기술 Bot: GitHub PR 제출 시 반드시 테스트 통과 스크린샷을 첨부합니다.
- 재무 Bot: 자금 조정과 관련된 사항은 반드시 확인 대기 항목으로 별도 분류합니다.

::: details 비서실장 아키텍처 및 부서 분할
```text
团队总体目标：
在两周内针对新上线的知识库产品，完成竞品定价调研，产出一份对比简报，并根据简报结构生成 3 篇官网更新草稿。

协作规则：
1. 调研 Bot 先行检索 5 家竞品公开定价，生成包含引用网址的 Markdown 表格。
2. 调研完成后在群内移交给内容 Bot，内容 Bot 根据数据起草 3 篇文案，放入指定 Notion 页面。
3. 幕僚长全程跟进看板状态，若遇到数据缺失，要求责任 Bot 重新抓取或报错，不得擅自编造。
4. 全流程中所有涉及对外发布的操作全部挂起，等待我在看板中勾选通过。
```
:::

**마음 놓고 노트북을 덮으려면 증거를 확인(Show the tape)하는 것이 전제되어야 합니다.** Bot 납품 시에는 세 가지 증빙 자료가 반드시 갖춰져야 합니다.

- 작업 화면 녹화 또는 호출 로그: 완전한 웹페이지 이동 궤적이나 도구 호출 시퀀스를 제시합니다.
- 데이터와 숫자의 원출처: 출처 없는 인용은 금지합니다.
- 오류로 인해 건너뛴 항목 및 추측성 결론에 대한 설명.

**신뢰는 4주에 걸쳐 단계적으로 이관합니다.**

1. 1주차 (초안 단계): Bot은 초안만 작성하고, 사람이 전체 내용을 정독한 뒤 수동으로 실행합니다.
2. 2주차 (승인 단계): Bot이 핵심 단계까지 실행한 후 멈추며, 사람은 작업 내용만 대조 확인하고 승인합니다.
3. 3주차 (이상 보고 단계): 저위험 작업은 자율 실행하며, 이상 징후나 권한 초과가 발생할 때만 팝업으로 도움을 요청합니다.
4. 4주차 (루틴 점검 단계): 정해진 루틴에 따라 완전히 자율 실행되며, 주말에 감사 보고서만 검토합니다.

## 1인 기업 실전: 단일 클라우드 컴퓨터의 경계와 독립 운영

### 물리적 경계

**동일 계정의 모든 Bot은 단일 컴퓨터를 공유**하며, 디렉터리와 세션도 함께 씁니다. 공식적으로도 Bot을 격리 경계로 간주하지 말 것을 명시하고 있습니다. 프롬프트만으로는 인젝션을 막을 수 없으며, 명령어를 잘못 실행하면 Cookie와 Session이 유출될 수 있습니다.

평소 세 가지 수칙을 준수하세요.
- 메인 인터넷 뱅킹과 핵심 코드 저장소에 로그인하지 않고, 기밀 클라우드 스토리지를 연결하지 않습니다.
- 외부 플랫폼은 최소 권한 서브 계정만 사용합니다.
- 외부 로그인은 Handoff 방식을 거쳐 사람이 직접 비밀번호를 입력하고, Bot은 Session만 상속받도록 합니다.

### API 미지원 시스템 자동화

**API가 없는 시스템은 컴퓨터 사용 역량을 활용해 클릭하고 양식을 작성**하므로, 다음 네 가지 업무를 먼저 인계하기에 적합합니다.
- 고객 확보 리서치: 커뮤니티 디렉터리를 스캔하고 이메일 초안 작성.
- 주문 이행 후속 조치: 품절 확인 및 지연 운송장 추적.
- 콘텐츠 일정 편성: 원고를 임시보관함에 등록.
- 코드 유지보수: 독립 쇼핑몰/웹사이트 오류 조사 및 패치 생성.

::: details API 미지원 시스템 자동화
```text
岗位名称：供应链履约跟踪员（Supplier Logistics Bot）
Owns：
每天上午 10:00 登录供应商门户，核对昨天未发货订单状态，提取物流单号，更新至运营表格。
Inputs：
供应商订货后台会话、本地待处理订单表格。
May：
在供应商后台查询订单状态、下载发货清单 CSV、更新本地表格对应列的运单号与发货时间。
Must ask before：
严禁点击「重新下单」或「取消订单」；严禁修改收货地址；若供应商后台提示账户欠款或商品缺货，停止处理并立即向我报警。
Done when：
所有处理过的运单在表格中均标注状态与回填时间；遇到后台页面改版导致按钮无法识别时，截取当前屏幕报错并退出，不得盲目重试。
```

## AI 에이전시 납품 체계: 월간 납품 파이프라인과 품질 검수 휴먼 게이트

![AI 에이전시 납품 체계: 월간 납품 파이프라인과 품질 검수 휴먼 게이트](/info/18-solo-s4.png)

여러 고객사를 대상으로 납품하는 AI 에이전시(AI Agency)의 핵심 난제는 다중 고객 동시 대응 시의 품질 안정성과 사용량 비용 제어입니다.

커뮤니티 작성자 maestro는 1인 체제로 5개 리테이너(Retainer) 고객사를 지원하며 월간 비즈니스를 운영하는 시스템 아키텍처를 공유했습니다(커뮤니티 작성자 maestro의 자체 보고: 월 매출 1.8만 달러, 5개 고객사 서비스, 미검증).

### 서비스 메뉴의 '3대 진입 테스트'

전면 맞춤형 주문을 받아 수작업 외주로 전락하지 마세요. **자동 납품 메뉴에 업무를 등록하려면 3가지 관문을 거쳐야 합니다**.

1. 브리프(Brief)를 구조화된 체크리스트로 작성할 수 있어야 합니다.
2. 납품물에 제3자 객관적 검수 기준이 있어야 합니다.
3. **이전에 순수 수작업으로 최소 10회 이상 납품해 본 경험이 있어야 합니다**. 10회를 채우지 못하면 마지노선을 파악할 수 없어 에이전트에 맡겨봤자 영양가 없는 결과물만 쏟아집니다.

기준을 통과한 업무로는 500K 컨텍스트로 40편의 자료를 대조하여 리서치 보고서를 작성하거나, 음성/톤 샘플(Voice File)에 맞춰 원고를 대량 작성하는 작업, 또는 대시보드 및 경량 스크래핑 도구를 구축하는 작업 등이 있습니다.

### 모델 라우팅과 19.5만 Token 요금 절벽 차단

모델은 작업에 맞춰 배분하고 플래그십 모델만 고집하지 마세요.
- Grok 4.1 Fast: 2M 컨텍스트, 데이터 정제 및 1차 스크리닝 담당.
- Grok Build 0.1: 개발 산출물의 80% 담당.
- Grok 4.6: 500K 컨텍스트, 장기 실행 Agent 및 추론 담당.

**입력이 200,000 Token을 초과하면 요율이 즉시 2배로 뜁니다**. 게이트웨이에 **195,000 Token 임계값을 하드코딩**하여 초과 시 오류를 반환하거나 잘라내기(Pruning)를 수행해야 합니다.

### 독립 읽기 전용 검토자와 3회 재시도 휴먼 게이트

> 출처: [How to Build an $18K/Month AI Agency on Grok (Exact Setup Inside)](https://x.com/maestrooth/status/2092658066714177657)  
> 작성자: [maestro @maestrooth](https://x.com/maestrooth)

![How to Build an $18K/Month AI Agency on Grok (Exact Setup Inside)](/cases-img/fs47-0.png)

![How to Build an $18K/Month AI Agency on Grok (Exact Setup Inside)](/cases-img/fs47-1.png)

생산 Bot이 자신이 만든 결과물을 검토하면 자기합리화 경향이 생겨 프롬프트 무력화를 덮어버리기 쉽습니다. **검토는 반드시 독립된 읽기 전용 루프로 분리해야 합니다**.

- 독립된 컨텍스트: 원본 브리프, 고객 규격, 산출물만 입력하고 중간 추론 과정은 제공하지 않습니다.
- 엄격한 읽기 전용: **결함을 발견하면 FAIL만 보고하고 절대 대필하지 않아**, 자체 수정으로 문제를 덮는 현상을 방지합니다.
- 대립적 트집 잡기: 치명적 결함을 집중적으로 찾아내며, 자료 근거가 없는 숫자는 무조건 불합격 처리합니다.

::: details 독립 읽기 전용 검토자와 3회 재시도 휴먼 게이트
```text
# 独立审查者审核准则（reviewer.md）
你是一名独立质量审查员，负责评估一份并非由你生产的交付产物。
你的唯一任务是找出交付物不符合客户要求的地方。你绝不需要去赞美它的优点。

输入物料：
原始需求 Brief、服务核对清单、客户品牌声音规范文件、最终交付草稿。
你未被提供、也严禁索取生产 Bot 的思考草稿。

审查规则（按顺序严格执行）：
1. 逐条核对需求 Brief 中的清单项。指出任何未被完全覆盖的要点。
2. 检查全文，严禁残留任何占位符文字、TODO 标记或括号说明文本。
3. 全文中的每一个具体数字、引文、统计百分比与人名，必须能在客户资料库中找到对应出处。发现任何未注明来源的数字，必须直接判定为 FAIL。
4. 语言风格是否符合客户过往已批准作品的语气标准。

输出格式：
第一行必须且只能输出一个词：PASS 或 FAIL。
如果判定为 FAIL，按以下格式列出所有缺陷：[清单条款] - [出现位置] - [具体问题及修正要求]。第一行后严禁输出任何空洞的总结段落。
若因上下文缺少凭据导致无法核验某一项，直接判定为 FAIL。
```
:::

```text
单任务自动化生产循环规则：
1. 生产 Bot 基于需求与声音规范生成第 1 版草稿。
2. 独立审核 Bot 执行审查。若返回 PASS，记录日志并进入待交付队列。
3. 若返回 FAIL，系统将审查不通过的具体原因拼接入下一轮 Brief，由生产 Bot 进行针对性修复重试。
4. 重试上限（MAX_ATTEMPTS）严格设定为 3 次。
5. 若连续 3 次均无法通过审查，系统立即终止自动重试，触发报警将原始 Brief、草稿与审查报错完整推送到人工桌面由人工兜底接管。
```

무한 루프로 막대한 Token 요금이 청구되는 것을 막기 위해 **인계 재시도는 최대 3회로 제한**합니다. 기계가 세 번 시도해도 기준에 미달한다면 요구사항이 충돌하고 있다는 뜻이므로 사람이 반드시 개입하여 판정해야 합니다.

## 29개 Agent 실전: 1인 체제에서 군단으로 유연하게 확장하는 법

![29개 Agent 실전: 1인 체제에서 군단으로 유연하게 확장하는 법](/info/18-solo-s5.png)

단일 직원의 설정과 2개 Bot의 품질 검수 루프에 익숙해지면, 비즈니스 수요에 따라 자연스럽게 팀을 확장하게 됩니다.

커뮤니티 작성자 Melvin Vivas는 Grok Bot을 29개의 전담 에이전트로 차근차근 확장해 나간 전체 실전 과정을 기록했습니다(커뮤니티 작성자 Melvin Vivas의 자체 보고: 29개 Bot 보유, 미검증).

### 29개 Agent의 직무 배치와 점진적 발전

**이 29개의 Bot은 모두 필요에 따라 자연스럽게 늘어난 것입니다.** 평소 반복적인 업무가 생길 때마다 전담 역할을 만들고, 역할이 많아지면 비서실장 Emma가 통합 관리하도록 했습니다. 비즈니스는 7대 영역으로 나뉩니다:

- 조율 중추: Emma가 전체 총괄 및 작업 분배를 담당.
- 기술 연구개발: CTO가 아키텍처를 총괄; **Coder는 Cursor를 호출하여 자동으로 코드를 작성하고 PR을 생성하며 오류를 수정**, 전 과정에서 로컬 편집기를 열 필요가 없음.
- 최신 리서치: 하루 종일 X 플랫폼의 오픈소스 동향을 모니터링하고 브리핑 작성.
- 콘텐츠 매트릭스: 채널별 원고 작성 및 회고 담당.
- 비즈니스 개발(BD): 비즈니스 기회 및 파트너십 리드 발굴.
- 운영 보안: 이메일, 백업 및 보안 검토 담당.
- 개인 성장: 루틴 체크, 시황 추적 및 의사결정 논증 처리.

### 멀티 Agent 협업 파이프라인: 기술 프로토타입에서 콘텐츠 전환까지의 예시

각 Bot은 공유 클라우드 컴퓨터와 세션 참조를 통해 바통을 이어받습니다.

::: details 멀티 Agent 협업 파이프라인: 기술 프로토타입에서 콘텐츠 전환까지의 예시
```text
端到端跨团队协同案例：
1. 【情报捕获】：X 调研员监控到某大模型最新发布，抓取官方文档与代码仓库地址，整理为技术要点。
2. 【任务调度】：幕僚长 Emma 捕获该报告，根据设定规则判定该模型具备测试价值，自动将任务下发给技术团队。
3. 【工程交付】：编码员 Coder 接收技术说明，调起 Cursor Cloud coding agent 在云端编写 Google Colab 演示笔记本，推送到 GitHub 仓库并自动创建 Pull Request。
4. 【排错闭环】：执行测试出现依赖包版本冲突，终端 Traceback 自动返回 Coder，Coder 修复代码再次提交 PR 通过测试。
5. 【内容物料转译】：PR 合并后，Emma 将成功代码仓库与技术参数推送给内容创作团队，YouTube 脚本助手与 X 内容经理在半小时内完成多平台发布草稿，存入指定待审目录。
6. 【人闸闭环】：创始人全程不介入代码编写与格式排版，仅在最后核验 Colab 实际运行效果，并点击确认对外发布推文。
```
:::

**수정 사항이 생겨도 29개 창을 일일이 열 필요 없이**, 총괄 Bot이 명령어 하나를 브로드캐스트하면 몇 초 만에 동기화할 수 있습니다.

### 역할 분할의 5가지 신호와 7단계 자동화 방법

평가 목표, 호출 도구, 업무 스타일, 승인 경계(초안 작성과 대외 커뮤니케이션은 절대 섞여선 안 됨), 스케줄링 주기가 다를 때는 반드시 **독립된 Bot으로 분할**해야 합니다.

1. 목표, 데이터 소스, 서식, 중단 경계를 Bot에 전달하여 기억하게 합니다. 공유 Bot은 상세 정보의 About에 작성합니다.
2. 제어 가능한 실제 작업을 선정하여 1회 실행합니다.
3. 수동 튜닝을 거쳐 무검수 수준까지 최적화합니다.
4. 재사용 가능한 Skill로 축적합니다.
5. 새로운 데이터로 교체하여 일반화 성능을 재검증합니다.
6. **재시도 상한 및 누락 알림을 설정한 후에 비로소 Routine을 활성화합니다**.
7. 이메일 발송, 결제, 시스템 변경 작업에는 반드시 Require Approval 휴먼 게이트를 강제 연동합니다.

| 단계 | 규모 | 아키텍처 및 병목 |
| :-- | :-- | :-- |
| 1단계: 1인 체제 | 1 Bot | 전면적인 휴먼 게이트 검증 루프; 상시 모니터링 필요 |
| 2단계: 소그룹 | 2-3 Bot | 생산과 검토 분리; 일일 유지보수 시간을 15분 이내로 단축 |
| 3단계: 비서실장 | 4-6 Bot | 분배 및 칸반 보드 관리; **비서실장이 잡무를 하지 않도록 차단** |
| 4단계: 군단 | 10-30 Bot | 다채널 스탠드업 미팅; 무효한 루틴 정기적 정리 |

### 칸반 보드 시스템과 일일 스탠드업(Morning Standup) 메커니즘

> 출처: [How I use Grok Bot: My team of 29 AI agents](https://x.com/melvindvivas/status/2109480575421808962)  
> 작성자: [Melvin Vivas @melvindvivas](https://x.com/melvindvivas)

Bot이 5개를 넘어가면 여러 채팅창을 쓰지 마세요. 도저히 다 확인할 수 없습니다. **멀티 Bot 협업은 주로 칸반 보드와 정기 점검이라는 두 가지 축으로 운영됩니다**:

- **상태 공유 칸반 보드**: 작업을 채팅 기록에 흩어두지 말고 Notion이나 데이터베이스 칸반 보드로 일원화하며, 5가지 상태를 정의합니다: `Todo`, `Working`, `Blocked`, `Ready for Review`, `Done`.

  Bot은 알 수 없는 오류나 권한 부족에 직면했을 때 즉시 `Blocked`로 상태를 변경하고 사람을 호출하므로, 평소에는 카드의 이동 흐름만 확인하면 됩니다.
- **정기 점검 및 대조**: 단일 Bot당 최대 50개의 Routine을 설정할 수 있으며, 최대 5분마다 1회 실행 가능합니다.

  **새벽 3:00에는 코드의 데드 링크와 패키지 용량을 자동 점검하고, 5:00에는 총괄 Bot(예: Jenny)이 전담 Bot들의 Playbook을 하나씩 대조 확인**하여, 시간이 지남에 따라 모델이 규칙을 망각하는 것을 효과적으로 방지합니다.

```text
全体专职 Bot，开始进行本周团队回顾审计。请各岗位汇报：
1. 本周你实际执行了多少次任务，其中失败或异常的中断有多少次？
2. 在执行过程中，有哪些步骤存在推测行为、跳过行为或由于数据缺失强行拼凑的情况？
3. 有哪些挂起的审批事项我一直没有回应？有哪些生成的物料我从来没有打开查看过？
4. 请指出：在当前的工作流中，你发现哪两个 Bot 存在职责重叠或重复工作？
5. 给出客观建议：为了节省整体用量额度，我们下周最应该裁撤哪一个无效的 Routine 或岗位？
```

## 빠지기 쉬운 함정

### 권한 및 승인
1. 클라우드 컴퓨터를 공유하면 Session이 격리 없이 공유되므로, **절대로 메인 계정과 민감한 시스템에 로그인하지 마세요**.
2. Require Approval은 아직 실행되지 않은 작업만 차단할 수 있을 뿐 파괴적인 작업을 되돌릴 수는 없으므로, **위험도가 높은 작업은 처음부터 엄격한 휴먼 게이트를 설정하세요**.
3. 승인 요청은 약 10분간 응답하지 않으면 만료(Lapse)되므로, 야간에는 **반드시 Allow rule 화이트리스트를 설정하거나 초안 단계에서 멈추도록 해야 합니다**.

### 비용 및 아키텍처
4. 입력이 20만(200,000) Token을 초과하면 단가가 2배로 상승합니다: **라우팅 계층에 195,000 Token 하드 차단 및 가지치기(Pruning)를 설정해야 합니다**.
5. 단일 Bot이 모든 일을 도맡게 하거나 범용 Bot 5개를 복제하지 마세요. **역할 분담이 불명확하면 컨텍스트만 오염되고 사용량이 낭비됩니다**.
6. 5분 주기 폴링이나 전체 메시지 수신 대기를 설정하지 마세요. **No-data policy가 없으면 네트워크 단절 시 데이터를 임의로 지어내어 사용량이 고갈되기 쉽습니다**.

### 규칙 및 인계
7. 채팅창에서 당부한 내용은 새로고침하면 사라지므로, **작업 전반에 걸친 규율은 Bot이 기억하도록 설정해야 합니다**. 공유 Bot은 상세 정보의 About에 작성하며, 개인 Bot에는 이미 Description이 없습니다.
8. Bot 간 인계 시 전체 대화 기록을 옮기지 말고, **인계 패키지에는 목표와 결과물 경로, 그리고 결론 및 다음 단계 요구사항만 남겨야 합니다**.

## 완료 후 검수 방법

1. **자격 증명 확인**: Plugins 및 브라우저에서 은행 및 메인 자격 증명을 삭제하고 서브 계정이나 Session을 사용하며, **채팅 기록에 평문 비밀번호를 절대 저장하지 않습니다**.
2. **역할 정의 검증**: Bot에는 반드시 Owns/Inputs/May/Must ask before/Done when이 포함되어야 하며, 말미에 드리프트 방지 문구를 추가하여 **데이터 누락 시 즉시 오류를 보고하고 임의 조작을 엄격히 금지**하도록 합니다.
3. **휴먼 게이트 테스트**: 결제나 삭제 명령을 내렸을 때 반드시 **100% Require Approval을 트리거하여 작업을 일시 중단**해야 합니다.
4. **검토 저항력 테스트**: 가짜 데이터 초안을 제공했을 때, 품질 검수 Bot은 **반드시 첫 줄에 FAIL을 반환**하고 임의로 수정하지 않아야 합니다. 3회 연속 실패 시 즉시 작업을 중단하고 알림을 발생시킵니다.
5. **안정적인 루틴 확인**: 칸반 보드 상태가 실시간으로 갱신되는지 확인하고, 활성화 전에 Test run을 클릭하여 정상 실행을 확인하며, **예약 작업이 10분을 초과하는 야간 승인에 의존하지 않도록 합니다**.
